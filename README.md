# sawdust

A Parquet reader written from scratch in Go, with no Parquet dependency — a
learning lab for the bytes underneath columnar storage.

Sawdust is what you get when you cut into parquet.

## Why

I build data pipelines that produce and consume Parquet daily. I know the
format from the top: schemas, partitions, predicate pushdown, compression
ratios. This project approaches it from the bottom: footers, Thrift compact
protocol, varints, bit-packing, dictionary pages, ZSTD frames.

The end product is a library plus a CLI that can:

- dump a file's schema, row groups, column chunks and statistics
- decode column values without any Parquet library in `go.mod`
- report per-column compressed/uncompressed bytes so storage decisions can be
  made from measurements instead of guesses

It exists to be *used*, not just written: the CLI is meant to become the tool
I reach for when inspecting output from
[machine-observability](https://github.com/sevaergdm/machine-observability).

## The method

Same approach as [linkcheck](https://github.com/sevaergdm/linkcheck): staged,
problem-first, and every stage has a **verifiable oracle**.

The oracle here is DuckDB. It reads the same files and exposes its own view of
the metadata:

```sql
SELECT * FROM parquet_file_metadata('f.parquet');  -- version, num_rows, created_by
SELECT * FROM parquet_schema('f.parquet');         -- one row per schema element
SELECT * FROM parquet_metadata('f.parquet');       -- one row per column chunk
DESCRIBE SELECT * FROM 'f.parquet';                -- resolved SQL types
```

Every stage's "Done when" is a comparison against one of those, or against
bytes computed by hand. There is no stage where correctness is a matter of
opinion.

## Rules of engagement

- **Sketch before code.** Each stage starts with a paper sketch: the types,
  the functions, one sentence each, and what the failure modes are. Review the
  sketch before writing the implementation.
- **Read real bytes early.** `xxd` a real file before writing a parser for it.
  Guessing from the spec alone wastes more time than reading 40 bytes.
- **Hand-build the fixtures.** Test inputs are generated by
  `cmd/genfix`, never copied from real data (real Parquet from the
  observability agent contains hostnames, unit names, and log text).
- **Stage 1 is test-first, deliberately.** The Thrift decoder is pure
  functions over byte slices — the cheapest place to build the habit.
- **Self-diff before every push.** `git diff` and read your own change as if
  reviewing someone else. Copy-paste survivors and stale labels are the most
  common defects in work like this.
- Bring finished stages up for review — pointers, not solutions.

## Layout (as it emerges)

```
cmd/sawdust/     the CLI
cmd/genfix/      fixture generator (uses parquet-go; the ONLY place it appears)
internal/thrift/ compact-protocol decoder
internal/format/ Parquet metadata structs
...
testdata/        generated fixtures, committed
```

`cmd/genfix` is the one exception to "no Parquet dependency" — it *writes* the
files the reader is tested against, using the same library that writes the
real data. Keeping it in its own `cmd` makes the boundary explicit: the library
being learned has zero Parquet dependencies.
